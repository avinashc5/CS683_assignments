\section*{Task 1A: IP-stride (baseline prefetcher)}
\texttt{ip\_stride.l1d\_pref} keeps 24 IP trackers (IP, last line address, last stride, LRU). On an access by a tracked IP it computes the stride from the last line; if it equals the stored stride it prefetches the next 3 strides ahead (same page only), otherwise it just stores the new stride. It therefore captures only a \emph{constant} stride and is blind to repeating non-uniform sequences such as $(1,2,3)^n$. It is tracked by a fully-associative LRU table of 24 entries, so IPs beyond 24 thrash it.

\section*{Task 1B: SPP design}
\begin{itemize}[nosep]
\item \textbf{IP table} (256 entries, direct mapped, 8-bit tag): last line (low 16 bits), last stride, a 2-bit uniform-stride confidence, and a signature of the last 3 strides (7 bits each).
\item \textbf{Pattern table} (256 entries) indexed by a hash of the 3-stride signature $\rightarrow$ (next stride, 2-bit confidence). A \textbf{fallback table} (64 entries) is keyed by the last 2 strides and is used when the 3-stride entry is not confident.
\item \textbf{Prediction}: if the uniform confidence is high the constant stride is used; otherwise the pattern table is walked, feeding each predicted stride back into the signature, up to the current degree. Prefetching stops at the 4KB page boundary and when the prefetch queue is full. Only loads/RFOs train. Prefetches fill L1D unless the MSHR is more than half full, then L2.
\item \textbf{Accuracy throttling}: a 64-entry filter of recently filled prefetch lines; a demand hit on it counts as useful. Every 256 prefetch fills accuracy is computed and the degree set: $\ge$75\%$\to$6, $\ge$50\%$\to$4, $\ge$25\%$\to$2, else 1 (initial 4).
\end{itemize}

Speedup = IPC / baseline IPC (mean = geometric). Coverage = (baseline L1D load misses $-$ misses with prefetcher)/baseline. Accuracy is the simulator's (useful / prefetches issued to the lower level).

\section*{Threshold and degree rationale}
Accuracy thresholds 75/50/25\% divide accuracy into four bands: above 75\% prefetches are almost always used, so aggressive depth (6) is cheap; 50 to 75\% is the normal band (4); 25 to 50\% means over half the prefetches are wasted, so depth is halved (2); below 25\% prefetching costs more bandwidth and L1D pollution than it saves, so only one line is issued. The values are round quartile boundaries; I validated them by sweeping: thresholds 50/30/10, 60/40/20, 90/70/40 and degree sets (8,4,2,1), (8,6,4,2) all lie within $\pm$0.1\% of mean speedup (1.0115 to 1.0129), so the result is insensitive to them. Fixed degrees 1/2/4/6 give mean speedups 1.0076/1.0091/1.0101/1.0102, so deeper is better up to 4, and flat beyond. \textbf{Honest finding:} dynamic throttling gives the same speedup as fixed degree 4 (1.0122 vs 1.0124) but 4 to 9 points higher accuracy, i.e.\ it saves bandwidth without losing performance.

\section*{Task 2A: Instruction-conscious L2 replacement (I-RRIP)}
All Task 2 runs use no L1D prefetcher, so the replacement policy is evaluated in isolation (Task 3 combines it with SPP). The baseline is LRU at L2.

{\sloppy \textbf{Exposing instruction information.} \texttt{update\_replacement\_state} was extended with a 9th parameter \texttt{isInstruction} for every cache (declarations in \texttt{inc/cache.h}, all \texttt{replacement/*\_repl} definitions). The six call sites in \texttt{src/cache.cc} pass the packet's \texttt{instruction} field (MSHR entry on fills, RQ/WQ/PQ entry on hits); the BTB calls in \texttt{src/ooo\_cpu.cc} pass 0. For eviction, the policy reads the per-line \texttt{BLOCK::instruction} bit, which \texttt{fill\_cache} already sets for L2C lines filled by instruction loads/prefetches, through the \texttt{current\_set} argument of \texttt{find\_victim}.\par}

\textbf{Policy} (\texttt{replacement/irrip.l2c\_repl}, 2-bit RRPV as in SRRIP):
\begin{itemize}[nosep]
\item \textbf{Insertion:} instruction lines at RRPV 1, data lines at RRPV 3 (SRRIP: both at 2).
\item \textbf{Promotion:} an instruction hit sets RRPV to 0; a data hit decrements RRPV by 1 (SRRIP: both to 0).
\item \textbf{Eviction:} among lines at RRPV 3, a data line is evicted before an instruction line; aging is unchanged.
\end{itemize}

\textbf{Findings.} I-RRIP reaches a mean speedup of 1.0112, against 1.0004 for SRRIP. It cuts the mean L2 instruction load MPKI from 9.91 (SRRIP) to 6.52 ($-$34\%), at the cost of data load MPKI rising from 5.98 to 7.68 ($+$28\%); total L2 load MPKI still falls 11\% (15.89 to 14.20), because instruction misses are both the larger share and the more costly ones (an instruction miss stalls the front end, while out-of-order execution hides part of a data miss). The gain is concentrated on Trace 2, the trace with by far the highest L2 instruction MPKI: instruction MPKI almost halves (17.98 to 9.44) and IPC improves 3.3\%. Trace 3 gains 0.2\%. Blindly prioritising instructions is therefore not always right, which is the motivation for Task 2B.

{\sloppy\textbf{How the design was chosen.} Every part of the policy was made a compile-time knob: instruction insertion RRPV (0/1/2), data insertion (RRPV 2 / RRPV 3 / bimodal: RRPV 3 with every 32nd insertion at 2), instruction promotion (to 0 / decrement), data promotion (to 0 / decrement / unchanged), and two eviction options (prefer a data victim among RRPV-3 lines; age data lines by 2 instead of 1). The full grid is $3\cdot3\cdot2\cdot3\cdot2\cdot2 = 216$ configurations, so the search was done in two stages. \emph{Stage 1} (14 configurations) turned on one change at a time, both on top of SRRIP (an ablation of insertion, promotion and eviction) and on top of I+P, the combination of instruction insertion at RRPV 0 (instruction hits to 0) and data decrement on hit. The all-SRRIP setting reproduces \texttt{rrip.l2c\_repl} exactly, which validates the knob implementation.\par}

\medskip
\textbf{Rationale: insertion (modified).} Insertion decides how long a line survives before it has proved itself, so it is the most direct lever for prioritising instructions. Code lines are reused across loop iterations and repeated calls, but often at reuse distances larger than the L1I. Inserting data at RRPV 3 makes a new data line the first eviction candidate unless it is reused; this was the largest single improvement in stage 1 (1.0058 to 1.0089), which indicates that most data lines reaching L2 in these traces are not reused before they would be evicted anyway. Instructions are inserted at RRPV 1 rather than 0. This is the one result that only the full factorial revealed: with data inserted at RRPV 2, instruction RRPV 0 was slightly better (1.0058 versus 1.0052), but once data is inserted at RRPV 3, RRPV 1 is better in all eight pairings, by 0.17--0.28\%. Data at RRPV 3 already gives code a two-step lead, so RRPV 0 is no longer needed to protect code from data; it only lets code that is fetched once (cold paths, one-time initialisation) push out code that is actually reused. Bimodal data insertion was within 0.04\% of RRPV 3 in every stage-2 pairing (and never better) but adds a counter, so plain RRPV 3 was kept.

\textbf{Rationale: promotion (modified for data only).} An instruction hit is strong evidence of a hot code path, so it keeps SRRIP's promote-to-0 rule. The decrement alternative tied (1.0059 versus 1.0058), so the simpler and standard rule was kept. Data uses frequency-based promotion: one hit moves a line one step nearer, so only repeatedly reused data earns the protection code gets on its first hit. Promoting data to 0 on a hit would undo the insertion bias after a single reuse; measured against decrementing, it lowered the mean speedup from 1.0058 to 1.0043. Leaving data unpromoted tied with decrement on its own (1.0059), but combined with insertion at RRPV 3 a reused data line could never leave the eviction position, so decrement is the safe choice.

\textbf{Rationale: eviction (modified as a tie-breaker only).} SRRIP evicts the first line it finds at RRPV 3. Preferring a data line among the RRPV-3 candidates costs nothing extra, because the instruction bit is already stored per line. It only matters when code and data are equally old, and then evicting the data line is consistent with the rest of the policy. On its own it gave the largest gain of any single change on top of SRRIP (1.0004 to 1.0058), and in stage 2 it added about 0.05\%. Aging data faster was \emph{not} adopted: on top of the chosen insertion and promotion it moved the mean speedup by at most 0.01\% (1.0112 versus 1.0113), but it raised the Trace 1 loss from 0.14\% to 0.26\% and needs a second aging rule. The aging procedure is therefore left as in SRRIP.

\textbf{Storage.} Per line: 2-bit RRPV (as SRRIP) and 1 instruction bit, which ChampSim's L2C already keeps in \texttt{BLOCK}. For 1024 sets $\times$ 8 ways this is 16384 + 8192 = 24576 bits (3 KB), of which only the 8192 instruction bits (1 KB) are on top of SRRIP. No counters or tables are added.

\section*{Task 2B: Dynamic I-RRIP}
Same setup as Task 2A (no L1D prefetcher, LRU baseline, 25M warmup + 25M simulation instructions).

{\sloppy \textbf{Policy} (\texttt{replacement/dyn\_irrip.l2c\_repl}; the prefetch rules added in Task 3 never trigger here, since no prefetcher is used): set dueling between SRRIP and I-RRIP.\par}
\begin{itemize}[nosep]
\item \textbf{Leader sets:} 32 sets always run SRRIP and 32 always run I-RRIP (64 of the 1024 sets, 6.25\%). The cache is split into 32 regions of 32 sets; in region $r$ the set at offset $r$ is the SRRIP leader and the set at offset $31-r$ (the complement) is the I-RRIP leader, so both groups are spread over the whole cache and never overlap. Identifying a leader is a 5-bit compare on the set index; no table is needed.
\item \textbf{Selector:} a 10-bit saturating counter PSEL, initialised to 512. A demand load miss in an SRRIP leader increments it, one in an I-RRIP leader decrements it. Follower sets (the other 960) run I-RRIP when the MSB of PSEL is 1 (the SRRIP leaders are missing more) and SRRIP otherwise.
\item \textbf{SRRIP mode:} insert at RRPV 2, promote to 0 on a hit, evict the first line at RRPV 3.
\item \textbf{I-RRIP mode:} instruction lines inserted at RRPV 1 and promoted to 0 on a hit; data lines inserted at RRPV 3 and decremented by 1 on a hit; among lines at RRPV 3 a data line is evicted first; when no line is at RRPV 3, data lines age by 2 and instruction lines by 1.
\end{itemize}

\textbf{Results.} ``I-RRIP mode, static'' is the I-RRIP mode above run on every set, to separate the effect of the selector from that of the mode itself.

\textbf{Findings.} The selector makes the right choice on every trace and never changes its mind after warmup. On Trace 1 the I-RRIP leaders miss 13\% more than the SRRIP leaders, PSEL sits at 0, and all follower sets run SRRIP: the Trace 1 loss shrinks from 0.26\% (I-RRIP mode, static) to 0.07\%, and data MPKI returns to the SRRIP level (7.14 versus 7.06). On Traces 2 and 3 the SRRIP leaders miss more (18\% and 6\%), PSEL saturates near 1023, and all followers run I-RRIP. Dynamic I-RRIP has the highest mean speedup of all policies (1.0114) and the lowest mean L2 load MPKI (13.90, against 14.20 for Task 2A's I-RRIP and 15.89 for SRRIP). The upper bound for any selector between these two modes, the better static mode on each trace, is 1.0121; the remaining 0.07\% is the cost of the leader sets, which keep running the losing policy (on Trace 2, the 32 SRRIP leaders lower the speedup from 1.0348 to 1.0335).

\textbf{Choice of the I-RRIP mode.} Task 2A and Task 2B use different I-RRIP settings, because the two tasks are asked different questions. In Task 2A the policy is static: whatever it does to a trace, that trace keeps it. So it was chosen on all three traces, and the setting without faster data aging was kept. Its mean speedup is within noise of the best one (1.0112 versus 1.0113), and it loses less on Trace 1 (0.14\% versus 0.26\%).

In Task 2B the I-RRIP rules are only one of two options. Set dueling falls back to SRRIP on a workload where they hurt. Trace 1 is such a workload: replacement barely matters there (SRRIP 0.9999 against LRU), and every I-RRIP setting was slightly below the baseline. For Trace 1 the dynamic policy should therefore pick SRRIP, not a gentler I-RRIP, which is what the selector table shows. The I-RRIP mode only needs to be strong on the workloads where it gets picked. Trace 2 is the case the problem statement describes: a large code footprint, with the highest L2 instruction MPKI under SRRIP (17.98). The I-RRIP mode is therefore tuned for Trace 2. Adding faster data aging raises Trace 2's speedup from 1.0334 to 1.0348 and cuts its instruction MPKI from 9.43 to 9.03. The cost is one extra aging rule, used only in sets running I-RRIP.

\textbf{How the design was chosen.} The number of leader sets, their placement and the PSEL width were made compile-time knobs. Two sanity runs force all follower sets into one mode; they reproduce static SRRIP and the static I-RRIP mode to within 0.05\% on every trace (the remaining difference is the leader sets of the other policy), which validates the mode switch.

\textbf{Rationale: number and placement of leader sets.} The leader sets are a sample of the cache, and the selector is only as good as the sample. Traces 2 and 3 are easy: every configuration picks I-RRIP. Trace 1 is the hard case, because the two modes differ there by only 0.25\%, so the miss counts of the two leader groups are close and the outcome depends on which sets are sampled. With 8 or 16 leaders per policy the answer depends on placement: contiguous leaders choose SRRIP, while spread leaders choose I-RRIP. Since the same number of leaders gives opposite answers, these samples are too small to be trusted. With 32 spread leaders the choice is SRRIP, while 32 contiguous leaders flip back and forth (60\% of the time in I-RRIP mode, 77 switches): sets $0..63$ are a narrow, unrepresentative slice of the address space, and spreading the leaders over all regions avoids that. 8 contiguous leaders had the highest mean (1.0119 versus 1.0114), but only because that particular small sample happened to choose correctly on Trace 1; 32 spread leaders were chosen because their Trace 1 choice does not depend on luck. The price is that more sets run the losing policy: on Trace 2, speedup goes from 1.0343--1.0346 with 8 leaders to 1.0335 with 32. Going beyond 32 would raise this cost further (more than 6\% of the cache would be fixed to the wrong policy) for a choice that is already stable.

\textbf{Rationale: PSEL width.} The width sets how many net misses are needed to change mode (half the range: 128 for 8 bits, 512 for 10, 2048 for 12). An 8-bit PSEL is too sensitive: with 32 spread leaders it still put 2.6\% of Trace 1 follower updates in I-RRIP mode, and with 32 contiguous leaders it switched 87 times on Trace 1 and 25 times on Trace 3, where it cost 0.33\%. At 10 and 12 bits the speedups are identical for every leader configuration (the only difference is 16 contiguous leaders spending 2.5\% of Trace 1 in I-RRIP mode at 10 bits, with no effect on IPC), so 10 bits is the smallest width at which the decision is stable.

% TODO: revisit if the ratio-threshold selector from the hint is evaluated
\textbf{Rationale: decision logic.} The selector compares the two policies directly, by the misses they actually cause in their leader sets, instead of predicting from the instruction share of accesses which policy should be better. This is what the problem asks for (reduce overall misses rather than favour instructions blindly), and it needs no threshold to tune: the decision follows from the outcome. Only demand load misses update PSEL, because they are the misses that stall the core; RFO, prefetch and writeback misses are mostly off the critical path and would bias PSEL toward a policy that reduces traffic rather than stalls. Instruction and data misses are weighted equally; a different weighting was not explored.

\textbf{Storage.} On top of Task 2A's per-line state (2-bit RRPV and the instruction bit, 24576 bits for 1024 sets $\times$ 8 ways), only the 10-bit PSEL is added: 24586 bits in total. Leader identification is combinational logic on the set index. The other counters in the code (follower updates, mode switches, leader misses) are simulation statistics and not part of the design.

\section*{Task 3: SPP with prefetch-aware Dynamic I-RRIP}
\textbf{Policy} (\texttt{replacement/dyn\_irrip.l2c\_repl} with \texttt{PF\_AWARE} 1; \texttt{PF\_AWARE} 0 gives the Task 2B policy). The Task 2B policy is kept unchanged (32 SRRIP and 32 I-RRIP leader sets, 10-bit PSEL), and two prefetch rules are added to the I-RRIP mode only, so the SRRIP leader sets still represent plain SRRIP in the duel. A prefetched data line is inserted at RRPV 3 (first eviction candidate), and a prefetch request that hits a resident line does not promote it. Everything else is the Task 2B I-RRIP mode: instructions inserted at RRPV 1 and promoted to 0; demand data inserted at RRPV 3 and decremented by 1 on a hit, so a prefetched line that is actually used moves up; among RRPV-3 lines a data line is evicted first, and data ages by 2. Because the Task 2B I-RRIP mode already inserts all data at RRPV 3, the insertion rule places prefetches at the same position as demand data; the prefetch-specific difference is that prefetch hits do not promote.

\textbf{Rationale.} SPP brings lines into L1D, so the L2 copy of a prefetched line is a duplicate that is only needed if the L1D copy is evicted before use; a speculative line should therefore not displace demand data or instruction lines, which the L2 is supposed to protect. A prefetch hit is not evidence of reuse (the prefetcher re-requests a line it already fetched), so promoting on it would keep stale lines alive. Inserting at the distant position lets a useless prefetch leave quickly, while a demand hit still rescues a useful one. The prefetch insertion RRPV was swept (1/2/3); RRPV 3 is best on mean speedup (1.0236 against 1.0223 and 1.0225), and inserting prefetches closer than demand data raises the L2 instruction MPKI (7.25 at RRPV 3, 7.31 at RRPV 1).

\section*{Limitations}
One 25M-instruction window per trace (the simulator is deterministic, but differences of $\sim$0.1\% may not generalise). ChampSim's warmup skips front-end stalls, so the measured region starts with caches and tables relatively cold; this affects all configurations equally. The accuracy counter does not track prefetches that fill L2. ChampSim seeds its random number generator from the trace file name (\texttt{src/main.cc}), and Task 2 was run with the traces named \texttt{trace1..3} while Tasks 1 and 3 used \texttt{Trace1..3}; each task is therefore compared against its own baseline run, and the same policy can differ slightly between tasks (Dynamic I-RRIP: 1.0114 in Task 2B, 1.0104 in Task 3).
